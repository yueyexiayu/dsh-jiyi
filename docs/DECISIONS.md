# jiyi 决策记录

记「为什么这样选」，不记「做了什么」——后者看 `README.md` 的版本说明和 `git log`。

每条格式固定：**背景 / 决定 / 后果**。后果要写清代价，不要只写好处。

编号 `D<n>` 只增不改。推翻某条决定时新增一条并写明「取代 D<n>」，不改原文。

## D1 — 召回排序用 RRF 排名融合，不用手调加权

**背景。** v0.1.35 之前是 `0.72·余弦 + 0.28·词法` 的加权和。问题出在两路分数量纲不可比：余弦是 0–1 的相似度，词法是以命中数计数的覆盖率。一个余弦为 0 但关键词精确命中的记忆，会被另一路的量级直接压到底，无论权重怎么调都救不回来——调权重只能改变被压制的程度，不能改变「压在同一个加法里」这件事本身。

**决定。** 两个通道各自排名，按 `1/(rrfK + rank)` 相加，`rrfK = 60`（`lib/retrieve.js` 的 `RETRIEVAL_CONSTANTS.rrfK`）。同分以上升 id 破平，使结果与输入顺序无关。

**后果。** 好处是融合只依赖排名、不依赖量纲，两路都能贡献候选，且结果可复现（I11 有专门测试守护）。代价是**丢失了分数的绝对信息**：原本「余弦 0.95」和「余弦 0.35」的差距，现在只剩名次差距。若将来某个通道需要表达「这条特别确定」，RRF 本身表达不了，得另加机制。另外 `rrfK` 是个需要调的旋钮，60 是常见默认值，本项目未做系统性扫参。

## D2 — 打包阶段用 MMR + factKey 限额，不用纯分数选取

**背景。** 纯按分数取前 6 条时，同一事实的多个版本会占满六个槽位。用户在几天里连续修正同一件事，六条记忆可能全是「我的偏好是 X」的六个历史版本，真正需要的另外五件事一条都进不来。

**决定。** 打包阶段用 MMR 贪心选取（`mmrLambda = 0.7`），并给同一 `factKey` 设上限 `candidateFactKeyCap = 2`。被限额挡掉的命中计入 `diversity.factKeyCapped`。

**后果。** 六槽的内容多样性有保证，且被挡掉的命中是**可见的**，不会被误报成「无相关记忆」（I12）。代价是 MMR 是贪心而非全局最优，且 `mmrLambda` 与上限都是手调值；上限设为 2 意味着「同一事实最多留两个版本」，对需要看完整版本谱系的场景偏紧。

## D3 — 前台召回截止「可缩短不可延长」

**背景。** 召回挂在用户回合的前台路径上。若配置值可以被运行期延长，一个慢模型就能把整轮对话拖住；用户在等待时并不知道 jiyi 正在检索。

**决定。** `effectiveRecallTimeout` 取 `min(configured, ceiling)`，`ceiling` 常态为 3000 ms。唯一例外：`embedder` 从未成功过时放宽到 10000 ms。超时、模型错误、判别失败一律 fail-open，不阻断对话。

**后果。** 配置只能收紧不能放宽，用户对最坏等待时间有硬保证（I6）。冷启动例外是必要的——本地模型冷加载要付进程启动加管线加载，塞不进 3 秒稳态预算，不放宽就等于「每个新会话第一次召回必然超时」。代价是**第一条召回可能慢到 10 秒**，且这个放宽只发生一次，之后回落到 3 秒。

## D4 — v4 使用独立数据目录 `storages/jiyi-v2`，从空记忆开始

**背景。** v0.1.34 引入了版本化证据、关系、有效期、待审冲突隔离和结构化决策日志。这些结构无法从旧库里「猜」出来——旧库只有无版本的正文，没有任何证据定位和 quote hash。就地升级意味着要么伪造证据元数据，要么在历史数据上留一堆无法验证的字段。

**决定。** 新数据目录 `storages/jiyi-v2/`，从空记忆开始；旧 `storages/jiyi/` 原样保留，不自动导入。首次启动沿用可读取的旧模型设置。

**后果。** 结构完整性有保证，每条记忆从一开始就带真实证据定位（I3 得以成立）。代价很直接：**升级用户的旧记忆不会自动出现在新版本里**，需要自行决定是否迁移。这是有意的取舍——宁可记忆少而可审计，不要多而无法追溯。另外磁盘上会同时存在两个数据目录，用户需要知道哪个是当前的。

## D5 — 待审冲突与提取队列分离，未裁决不进自动召回

**背景。** 两条记忆互相矛盾时，最省事的做法是「新的覆盖旧的」。但这个判断在证据不足时会出错：用户可能只是在不同项目里说了不同的话，而不是改变了主意。自动覆盖一旦错了，纠正成本很高——旧事实已经没了。

**决定。** 冲突候选进独立队列，与提取队列分开；未裁决的候选不进入自动召回（I14），也不放宽事实键唯一索引。裁决需要用户的清晰证据加明确时间；后台裁决在路由缺失、超时、非法 JSON、虚构引用、版本竞态或隐私变化时保持隔离并记录真实失败。

**后果。** 宁可短暂缺一条记忆，也不静默写错一条（对齐 I2「相似度不授权注入」的同一取向）。代价是**冲突会让相关事实暂时不可用**，直到裁决完成；用户可能感知为「刚说的偏好没生效」。缓解手段是面板里能看到待审冲突与裁决过程，把「为什么没生效」变成可查的，而不是让用户猜。

## D6 — 裁决探针判语义，不比对 `reasonCode` 文本

**背景。** 最初的 `verifyAdjudication` 探针同时固定 `decision=same_claim_newer` 和模型自造的 `reasonCode=newer_user_evidence`。`reasonCode` 是模型写的自由文本，固定它等于在考措辞而不是判断；在严格模型下这条探针会稳定失败，而配置其实是对的。探针一旦常年红着，用户就会忽略它，验证等于没有。

**决定。** 探针改为给旧记忆更早的明确用户证据、给候选更晚的证据，接受 `same_claim_newer` **或** `temporal_change`（store 两者同走替代路径），只校验引用同时命中 `memory:validation-memory:1` 与 `candidate:validation-candidate:candidate`，不再比对 `reasonCode`。一次不通过重试一次。同时给裁决子调用固定**最低推理档**——适配器默认高档时隐藏推理会吃光 `maxTokens`，流以 max-tokens 结束且没有任何 JSON。

**后果。** 探针测的是「这个配置能不能正确判断谁更新」，不是「模型会不会说某句话」，在严格模型下也能通过。代价是判定放宽了一个枚举值（`same_claim_newer` 与 `temporal_change` 都算过），理论上更弱；但两者在 store 层走同一路径，判别上的差别不对应用户可见行为。重试一次意味着**最坏情况探针耗时翻倍**。

## D7 — 设置写入是补丁，空补丁才是「恢复默认」

**背景。** v0.1.37 及之前，`op=settings` 直接走 `validateSettings(body.settings)`，而它从 `clone(DEFAULT_SETTINGS)` 起算。于是一个只想改 `retrieval.timeoutMs` 的调用方会把 `adjudication.minConfidence`、`consolidation`、`extraction` 全部悄悄重置成默认值，接口还返回 `ok:true`。用户永远看不到这次重置。

**决定。** 新增 `mergeSettings(current, patch)` 按段落浅合并。唯一的例外是空补丁 `{}`：它表示「恢复默认」，直接写 `DEFAULT_SETTINGS`。

**后果。** 部分提交不再破坏其它段落，而 `{}` 这个既有契约（多个测试依赖它做「整体重置」）保持不变。代价是语义分叉：空对象与「什么都不改」在直觉上应该等价，这里却被定义为相反的意思。这个歧义无法消除——两种含义都有人依赖——所以必须写进文档（`docs/API.md`）而不是留给调用方猜。

## D8 — 待审记忆的普通更新被拒绝，而不是静默结案

**背景。** 一条 `reviewState='pending'` 的记忆如果被普通更新（后台整理给出的 `user-explicit` 证据），旧实现会解散冲突组并把 `review_state` 改回 `clear`，未裁决内容立刻进入自动召回。若换成「允许更新但保留 pending」，冲突组指向的旧版本已经不存在，裁决时会 `CONFLICT_STALE`，成为永远无法处理的死组。

**决定。** 普通更新直接拒绝，抛 `CONFLICT_REVIEW_OPEN`。三类调用方可以结案：带 `user-correction` 证据的明确纠正、带裁决租约（`conflictGroupId`）的裁决路径、显式传 `resolveConflicts: true` 的调用方（手动纠正接口与巩固路径）。结案后由 `_syncReviewState` 按现存冲突组重新推导 `review_state`。

**后果。** 隔离既不会被静默抹掉，也不会留下死组或孤儿 pending——三个问题一次解掉。代价是后台整理碰到待审记忆时会失败重试，直到用户裁决；这条失败会进 `attemptHistory`，在面板可见。另一个代价是 `putMemory` 的默认行为从「更新优先」变成「冲突优先」，任何新调用点都必须显式声明它是否有权结案。

## D9 — 偏好类矛盾只靠 factKey，不做词法相似度扫描

**背景。** 审计建议把 `preference` 也纳入语义冲突扫描，否则用户先说「依赖统一用 npm」再说「依赖统一用 yarn」会留下两条互相矛盾、都能被召回的记忆。实现后立刻暴露问题：中文偏好句式高度同构，`我长期偏好中文回复` 与 `我长期偏好简洁报告` 在 token 层面的相似度，和 `依赖统一用 npm 安装` 与 `依赖统一用 yarn 安装` **完全一样**（共享「我长期偏好」「依赖统一用」「安装」这些模板成分）。关掉 `distinctSubjects` 过滤后，两条无关偏好被判为冲突，把一条健康记忆推进待审，`test/recovery.test.mjs` 的重启恢复测试直接失败。

**决定。** 回退词法扫描，`preference` 只保留 `factKey` 相同的判定。`status` / `decision` / `project_fact` 仍走语义扫描——这些类型的表述更「实」，模板成分少，词法差异能反映实际分歧。

**后果。** 同一槽位的偏好若被模型取了不同 `factKey`，仍然不会自动进待审，用户需要手动纠正。这是有意选择：**漏报一次可以由用户补救，误报会把正常记忆隔离起来，而用户不知道原因**。真正的解法是让 `factKey` 对偏好更稳定（在提示词里固定槽位命名），那是另一项工作。

## D10 — 4xx 是配置错误，内部故障是 500

**背景。** 两个方向都错了。`classifyFailure` 没有 4xx 分支，密钥失效（401）、模型名写错（404）、余额不足（402）全部落到 `unknown`，而 `unknown` 是可重试的——于是整个抽取队列按 10 秒起指数退避重试到耗尽，面板显示「暂时性故障」，用户永远不知道该改配置。同期 `5xx` 的正则只测 `message` 不测 `code`，provider 把状态写进错误码（`HTTP502`）时也认不出来。

另外 HTTP 层把所有错误一律映射成 400：磁盘 `EACCES`、SQLite 损坏、生命周期 `AggregateError` 都被报成「参数错误」，客户端和日志的排查方向完全错位，自动化重试逻辑也不会对 400 重试。

**决定。** `classifyFailure` 增加 `clientStatus` 与 `CLIENT_CODES`：4xx（429 除外）与常见认证类错误名判为 `configuration`，不可重试。5xx 正则同时测 `code` 和 `message`。路由层按错误码分层：`NOT_FOUND` → 404，`BUSY`/`EVAL_BUSY` → 409，`E*`/`ERR_*`/`SQLITE_*` → 500，其余 → 400。

**后果。** 配置错误会立刻失败并在 `failure.category` 里说明是配置问题，不再白白消耗重试预算。代价是**某些被 provider 包在 4xx 里的瞬时问题也不再重试**——这需要 provider adapter 把可重试的 4xx 单独标出来，而不是靠插件猜。HTTP 500 让真正的服务端故障可见，但也意味着任何非预期错误码都会变成 500，前端需要能处理它。
